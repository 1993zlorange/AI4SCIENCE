## 0. 与全局项目 Agent 的边界

本文件的四个 SR Agent 只负责科研内容、科研证据和科研项目内的交接；它们不是科研工作台软件的需求、架构、实现或独立验收责任人。全局 `.codex` 中与科研流程相邻的角色如下。

| 角色或能力 | 实际调用名 | 何时接入 | 输入 | 输出 | 不替代的职责 |
|---|---|---|---|---|---|
| 科研项目负责人 | `sr-research-project-lead` | 盘点项目、判断 Gate、给 P0/P1 或经授权派发 SR 工作流 | 成效卡、交接书、原始证据 | RPL-01～04 评估或派单结果 | 不直接生产 SR 叶子成果，不管理软件交付 |
| 首席研究员 | `sr-principal-investigator` | 研究问题、证据门、claim、路线和归档决策 | 已验证的研究输入和上游交接 | PI-E01/PI-X01/PI-P01 成果与交接书 | 不编写软件需求或实施代码 |
| 方法构建者 | `sr-method-builder` | 文献、假设、模型、实现契约、方法写作 | 研究问题、文献与设计证据 | MB-E01/MB-X01/MB-P01 成果与交接书 | 不替代软件架构评审或产品实现 |
| 实验员 | `sr-experimenter` | 实验设计、运行、数据质控、分析和图表 | 已冻结的实验设计、数据与资源许可 | EX-E01/EX-X01/EX-P01 成果与交接书 | 不自行扩大实验资源或产品范围 |
| 批判性评审员 | `sr-critical-reviewer` | 有效性、归因、完整性和稿件风险独立审查 | 产出方的可追溯成果 | CR-E01/CR-X01/CR-P01 成果与交接书 | 不替代产出方，也不修改其成果 |
| 项目经理 | `project-manager` | 研究成果将改变科研工作台产品需求、范围、验收、发布或阶段汇报时 | 已确认的科研转化意图、证据边界、用户决定 | 需求理解契约、PRD/SRS、计划、验收与状态材料 | 不把科研推断直接当作软件需求或验收通过 |
| 项目架构能力 | `$project-architect-agent` Skill | 已确认需求需要模块、接口、数据、迁移或 SDD 决策时 | 已确认需求、现有仓库和架构证据 | 架构方案、SDD、ADR、实施顺序 | 当前不是独立注册的全局 Agent |
| 全栈工程师 | `engineer` | 需求与架构已确认，需要实现科研工作台功能时 | 已确认需求契约、SRS/SDD、验收条件 | 代码、测试、浏览器证据、用户手册更新 | 不自行定义范围或独立验收 |
| 项目测试 | `project-test` | 需要对已实现的 Must 范围作独立功能验证时 | SRS/SDD、手册、实现和隔离测试环境 | PASS/FAIL/BLOCKED 与可复现缺陷 | 不修改产品代码、文档或正式数据 |

科研到软件的交接先由人确认研究结论是否要转化为产品目标，再调用 `project-manager` 形成需求理解契约。只有需求确认后，才进入 `$project-architect-agent`、`engineer`、`project-test` 的软件交付链。任何 SR 成效卡、仿真图或论文草稿都只能作为需求/设计证据候选，不能自动证明软件需求已批准、代码已实现或产品已验收。

## 2. 产物放置规则

### 2.1 每个 SR 工作包一张独立成效卡

每个实际调用并关闭的 SR 叶子工作包输出自己的成效卡：

```text
SR-<两位编号>-<成果简称>.md
```

例如：

```text
01-研究问题与选题/SR-02-碳硅异质融合热设计问题形式化.md
03-Idea与科学假设/SR-16-G1核心假设-v2.md
05-实验设计与执行/SR-34-555工况主对比.md
```

修订版必须保留 `SR-NN-` 前缀，例如 `SR-16-G1核心假设-v2.md`，不得覆盖已经被引用或验收的版本。旧式 `SR-NN_*.md` 文件只作为历史证据，不自动视为本规范成效卡，也不静默改名。

### 2.2 成效卡进入八类科研方面目录

Agent 先按数字前缀寻找现有目录，保留项目已有别名。例如 AI4CAE3 的 `03-Idea与科学假设` 等价于“03-Idea科学假设与创新点”，不另建重复目录。

## 3. 流程前后关系

```text
PI-E01
  -> MB-E01 <-> CR-E01
  -> EX-E01
  -> PI-X01（研究设计冻结 Gate F）
  -> MB-X01
  -> EX-X01
  -> CR-X01
  -> PI-X01（结果分析 Gate）
  -> EX-P01 + MB-P01
  -> PI-P01（主张与稿件初版）
  -> CR-P01
  -> PI-P01（修订、报告、归档）
  -> 下一周期 PI-E01
```

这不是只能向前的直线。批判性审查或 Gate 失败时，交接书必须明确退回哪个工作流。被重新打开的工作流除固定前置输入外，还要读取所有明确退回给自己的后续交接书。

## 4. 检索与读取规则

1. 对表中每个 SR 编号，在其八类方面目录内检索 `SR-NN-*.md`。
2. 同一 SR 有多个版本时，读取全部未明确作废版本，按卡内 scope、status、human verdict 和证据链选择当前版本，不按修改时间猜测。
3. 对表中每个工作流目录，按文件名时间顺序读取全部 `*.md` 交接书，再处理文中明确的 supersedes 关系。
4. 每次 work contract 和新交接书必须记录 `cards_read`、`handoffs_read`。
5. 卡或交接书缺失、断链、相互矛盾时必须报告，不能用聊天记忆补齐。
6. 读取成效卡后还要抽查其引用的原始论文、数据、代码、配置、日志或图，不能只读摘要。
