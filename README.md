# AI4SCIENCE

面向 AI for Science 与计算科研项目的可治理研究模板。它将项目监理、科研角色协作、可复现实验工程与阶段证据门组织为一套可追溯的工作方式，帮助研究者从一个尚未定义课题的空白项目开始推进研究。

> **模板状态：** `v0.1.0` 已作为本地 MIT 模板发行版准备；它不包含已批准的研究问题、假设、数据、实验、结果、论文或人工学术决定。目录、Agent 规则和示例结构不是科研成果，不能据此作出科学主张。

## 适用范围

适用于需要形成研究问题、文献证据、方法设计、可复现实验、结果审计、论文材料与阶段决策的 AI for Science 项目，例如算法研究、数据驱动科学建模、科学软件和计算实验项目。

不适用于跳过研究设计冻结、数据许可/伦理审查、实验记录、独立批判性评审或导师决定的研究流程。具体领域、数据、模型、计算资源、统计方法、投稿和开源策略必须由实际项目单独批准。

## 核心原则

- **范围明确再推进：** 项目监督能力核对授权、路径和完成条件；普通小修在现有范围继续，不机械新增角色或成套记录。
- **科学决策归人：** 研究问题、假设、数据纳入、资源投入、结果解释、主张强度、署名、投稿和公开发布由博士生或导师作出明确决定。
- **工作流有主责：** 科研项目负责人负责阶段判断与交接验收；首席研究员、方法构建者、实验员与批判性评审员各自拥有唯一工作流。
- **证据与阅读分开：** 工程实现、正确性检查与原始运行留在 `project/`；科研日志只写研究要点和性能进展。专题正文/图表在 `achieve/` 持续维护，日记录只引用。
- **同日同类一份：** 整个项目同一天同一规范记录类型只有一个可编辑文件，不按任务、Agent、阶段、目录或格式拆分；有真实内容才创建。
- **失败可回退：** 评审否定、实验失败或阶段门未通过时，回到对应责任工作流，不用后期论文或图表倒推前期工作已完成。

完整治理规则以[根级 Agent 协同规则](AGENTS.md)为准。

## 快速开始

### 1. 建立派生项目

以本模板创建真实研究时，将 `projectname` 替换为经批准的项目目录名；不要将开发机绝对路径、秘密、未获许可的数据或未经证实的科学结论写入模板规则。同时设置record_policy.project_id和目录映射；本模板已有维护日记录在派生项目中以精确legacy_paths登记为只读来源，不改原文，也不以目录前缀豁免将来新记录。

```text
AI4SCIENCE/
└── <实际项目名>/
    ├── project/    # 科研实施：代码、数据处理、实验、测试、配置和可复现运行证据
    └── achieve/    # 科研成效：成果卡、交接书、报告、论文材料和项目管理记录
```

首次操作前，读取：

1. [根级 Agent 协同规则](AGENTS.md)
2. [工程级 Agent 规则](projectname/project/AGENTS.md)
3. [工程编程规范](projectname/project/PROGRAMMING_STANDARDS.md)
4. [科研工程模板 README](projectname/project/README.md)

### 2. 启动研究

新项目没有既有证据时，应如实标记为 `new_project`，并从探索阶段开始：

```text
调用 pr-ps-00-project-supervisor 登记研究启动需求、范围、权限、目标目录和日志位置
  -> 调用 sr-research-project-lead 执行 RPL-01、RPL-02、RPL-03 的只读评估
  -> 由博士生或导师确认首个 P0
  -> 按批准范围执行，必要范围说明追加当天工作契约条目
  -> 同一批准批次持续完成单元、必要修复、恢复和汇总
  -> 每个真实科研叶任务保持独立结果条目；真实交接再追加交接条目
  -> sr-research-project-lead 核对实际结果，必要记录按日/类型追加，不补齐文档套件
```

没有“执行、派发、按建议推进”等明确授权时，科研项目负责人只能评估阶段并给出 P0/P1 建议，不能自行启动实验或后续工作流。

## 十二个科研工作流

工作流是可回退的依赖关系，不是必须一次运行到底的流水线。每项工作基于实际可读的上游材料和必要人工决定推进；旧卡片可继续引用，缺少指定表格不等于没有科研结果。

| 阶段 | 工作流 | 主责 Agent | 交付重点 |
| --- | --- | --- | --- |
| 探索 | PI-E01、MB-E01、CR-E01、EX-E01 | 首席研究员、方法构建者、批判性评审员、实验员 | 收敛问题、形成证据与假设、独立挑战、设计最小证伪。 |
| 执行 | MB-X01、EX-X01、CR-X01、PI-X01 | 方法构建者、实验员、批判性评审员、首席研究员 | 冻结实现契约、完成实验矩阵、审计完整性并执行结果证据门。 |
| 表达 | EX-P01、MB-P01、PI-P01、CR-P01 | 实验员、方法构建者、首席研究员、批判性评审员 | 完成核心图与定量分析、可复现写作、主张收敛和独立同行评审。 |

```text
PI-E01 -> MB-E01 <-> CR-E01 -> EX-E01 -> PI-X01（Gate F）
      -> MB-X01 -> EX-X01 -> CR-X01 -> PI-X01（结果证据门）
      -> EX-P01 + MB-P01 -> PI-P01 -> CR-P01 -> PI-P01
```

工作流的最低输入、日记录落点、科学检查点与人工权限见[根级 Agent 协同规则](AGENTS.md#5-十二个专业科研工作流)。

## 项目结构

```text
AI4SCIENCE/
├── AGENTS.md                         # 科研治理入口、Agent 路由、阶段门和交接规则
├── README.md                          # 模板入口说明（本文件）
├── projectname/
│   ├── project/                       # 科研实施目录
│   │   ├── src/                       # 算法、应用、数据、评估、追踪和产物管理
│   │   ├── configs/                   # 非敏感配置、功能登记和实验配置
│   │   ├── tests/                     # 单元、契约、集成、端到端与回归测试
│   │   ├── docs/                      # 工程架构、API、算法、ADR 和运行说明
│   │   ├── scripts/                   # 受控开发、运行、治理和迁移脚本
│   │   ├── benchmarks/                # 性能测量，不代替正确性测试
│   │   └── var/runs/                  # 本地运行产物；真实数据不提交 Git
│   └── achieve/                       # 正式科研成效和项目管理记录
│       ├── 00-项目管理/               # 需求、监督、日志、反思、质量、变更和成本
│       ├── 01-研究问题与选题/         # 问题定义与批判性评审材料
│       ├── 02-文献调研与领域结构/     # 文献证据与领域结构
│       ├── 03-Idea科学假设与创新点/   # 假设、创新点与边界
│       ├── 04-技术方案与方法设计/     # 方法、实现契约和设计材料
│       ├── 05-实验设计与执行/         # 实验计划、运行和质量控制
│       ├── 06-结果分析与问题诊断/     # 分析、诊断和核心图
│       ├── 07-论文与成果表达/         # 写作、审查和交付材料
│       └── 08-项目推进与下一步计划/   # 阶段决定、P0/P1 和路线计划
```

工程目录的算法、数据、评估、运行产物和测试放置规则见[工程级 Agent 规则](projectname/project/AGENTS.md#2-文件选择规则)。八类专题正文的 SR 内容范围映射见[根级规则](AGENTS.md#8-八类成效目录与命名)。

## 证据、可复现性与质量门

需要正式范围记录时，将目标、输入、授权资源、预期结果和停止条件追加到当天契约文件。每个真实科研叶任务是独立结果条目，不是独立文件；实际交接才写交接条目。科研成果卡、契约和交接各类型统一到08的日文件，SR/角色/状态放条目内，实际正文仍归八个专题。

工程实现前，在 `projectname/project/configs/features.yaml` 登记功能编号、代码、中文名称、责任人、实现路径、测试路径和状态。工程变更完成后运行：

```bash
python projectname/project/scripts/f001_governance_validate.py --project-root projectname/project --check
```

F001只读检查功能与已声明路径、作用域内文件唯一责任、当前入口、启用后的日记录/条目/文件锚点。已有历史原件兼容，不自动迁移或补写；检查不替代科学数据质控、性能比较、统计审计和导师决定。真实实验的代码版本、配置、输入摘要、环境、指标、日志与产物应按唯一 `run_id` 关联；运行命令、数据许可和资源要求由具体项目的工程 README 与工作契约提供。

## 当前入口与实验优先顺序

真实派生项目的根README只维护当前报告、性能总览和科研进度三个主要阅读入口；在 `record_policy.current_entries` 填入真实存在的文件路径。模板无科研结果，此映射保持空，不创建虚假报告。

科研负责人在05维护唯一已批准性能队列。先分析已有结果，再选择最能改变核心判断的一个缺口，写清研究要点/出处、比较对象、指标、预算和完成条件。内部实现检查不是先进性成果。已批准矩阵内的必要修复、断点恢复与汇总不算新研究，不反复要求原批准；真正的资源/权限/科学条件变化只暂停受影响分支。

长实验的状态与恢复必须独立于对话：每个单元保留真实终态，恢复核对输入/代码/配置并跳过已完成单元。工具等待超时不等于运行终止；运行完成、研究任务完成和科学接受状态分别记录。

## 文档与项目记录

| 内容 | 位置 | 规则 |
| --- | --- | --- |
| 必要项目记录 | `achieve/00-项目管理/` | 真实内容触发，同日同类型唯一；不每次操作生成需求/监督/日志/质量/成本各一份。 |
| 科研成果卡、契约、交接 | `achieve/08-项目推进与下一步计划/` | 各类型每日一份，多个任务是独立条目与稳定锚点，角色/工作流不拆文件。 |
| 研究设计与科研表达 | `achieve/01-*` 至 `achieve/08-*` | 通过项目相对路径引用工程证据，不复制出第二事实源。 |
| 工程技术文档与运行证据 | `project/docs/`、`project/var/runs/` | 与代码同生命周期维护；运行产物和真实数据不作为模板成效文件提交。 |

记录文档采用策略固定名称 `YYYYMMDD-固定主体-规范类型.md`，例如 `YYYYMMDD-科研进度-日志.md`；专题正文和正式交付仍用 `YYYYMMDD-内容简述-文档类型.扩展名`。`README.md`、`AGENTS.md`、`SKILL.md`、`pyproject.toml` 等固定入口文件可以保留稳定名称，但仍受归属、中文正文、变更和验证规则约束。

## 贡献与扩展

1. 开始前读取根级与工程级 `AGENTS.md`，通过项目监理登记工作范围和验证方式。
2. 科研推进先由 `sr-research-project-lead` 判断阶段和可执行的 P0/P1；涉及科学结论、资源或阶段门时保留人工检查点。
3. 在责任目录中修改代码、数据处理、实验、文档或治理记录，并补充相应的测试、运行或审查证据。
4. 如实记录已执行动作、原因、预期/实际影响、受影响需求、文件与下游；不把未执行检查、计划或推测写成事实。

新增文档型 Skill 必须随 Skill 提供中文结构化空白模板；新增脚本必须提供中文 API 说明、参数化相对路径、安全默认值和验证证据。项目级 Skill 晋升到全局前需要试点、独立评审、安全扫描、人工批准、版本/哈希和回滚证据。
